# ADR-001: 采用模块化单体而非微服务

- **Status**: Accepted
- **Date**: 2026-07-24

## Context

XCMS 需要服务于集团及多个子公司，包含租户管理、权限、流程、消息等 13+ 模块。团队面临架构选择：单体还是微服务。

集团需求包括：
- 独立部署能力（子公司可独立部署）
- 跨模块协作（如跨租户流程）
- 快速交付（0→1 阶段）

## Decision

采用 **Modular Monolith（模块化单体）** 架构：所有模块集成在一个 Java 应用中，通过 Maven/Gradle 多模块组织，模块间通过接口调用。

## Alternatives

### 方案 B：微服务

每个模块独立服务，独立部署。

- **优点**：独立扩缩容、技术栈灵活、团队并行
- **缺点**：起步成本高、跨服务调用复杂（网络开销、分布式事务）、独立部署子公司需部署多个服务、调试困难

### 方案 C：单体（无模块边界）

传统单体，无模块化设计。

- **优点**：最简单
- **缺点**：无法演进、代码耦合严重

## Consequences

### 正面

- 起步成本低，一个 JAR 部署即可
- 模块间方法调用（纳秒级），无网络开销
- 本地事务，无需分布式事务
- 独立部署子公司极简（同一份代码改配置）
- 调试简单（一个堆栈）

### 负面

- 无法独立扩缩容单个模块
- 全部技术栈绑定 Java
- 任何变更需全量重新部署

### 缓解措施

- 模块边界严格设计（API/Impl 拆分），保障未来可拆分
- 预留演进路径：单体 → 按需拆分 → 完整微服务
